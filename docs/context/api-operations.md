## 1. Rate Limiting (DAT-15)

> Anexo 07 DAT-15: Documented API rate limits to prevent ETL blocking.

The platform uses a tiered `ThrottlerGuard` (global, all endpoints).

| Tier | Window | Limit | Scope |
|------|-------:|------:|-------|
| short | 1s | 10 req | Per IP (or per API key) |
| medium | 60s | 100 req | Per IP (or per API key) |
| long | 3600s | 1000 req | Per IP (or per API key) |

### API Key Rate Limits

Each API key has a configurable `rate_limit_per_minute` (default 100).
Exceeding the limit returns `429 Too Many Requests` with `Retry-After` header.

**Storage:** Redis-backed (distributed, multi-instance safe) when `REDIS_URL` is set.

### Recommendations for PASA ETL

- Use **incremental loading** (see below) to minimize request volume
- Request a dedicated API key with higher `rate_limit_per_minute` for bulk ETL
- Implement exponential backoff on 429 responses
- Prefer `/v1/readings/aggregated` over raw readings for analytics
- Use `/v1/exports` for large dataset extraction (async job → download)

## 2. Incremental Data Loading (DAT-21)

> Anexo 07 DAT-21: Support for incremental extraction (only new data since last query).

### Pattern: Date Range Cursor

All time-series endpoints accept `from` and `to` ISO 8601 parameters:

```
GET /api/v1/readings?meterId=<uuid>&from=2026-06-14T00:00:00Z&to=2026-06-15T00:00:00Z
GET /api/v1/readings/aggregated?interval=hourly&from=2026-06-14T00:00:00Z&to=2026-06-15T00:00:00Z
```

### Recommended ETL Flow

```
1. Store last successful extraction timestamp (watermark)
2. Query: from=watermark, to=NOW()
3. Process response
4. Update watermark to MAX(timestamp) from response
5. Repeat on schedule (e.g., every 15 minutes)
```

### Latest Anchor

Use `GET /api/v1/readings/latest-anchor` to get the newest reading timestamp.
This avoids querying into the future and handles gaps.

### Bulk Export (Async)

For large extractions (>10K readings):

```
1. POST /api/v1/exports { format: "csv", from, to, meterId? }
2. GET /api/v1/exports/:id  → poll until status = "completed"
3. GET /api/v1/exports/:id/download  → stream CSV file
```

### Cursor-Based Pagination

The streaming export endpoint supports cursor-based pagination:

```
GET /api/v1/readings/export?format=csv&from=...&to=...&cursor=<last_id>
```

Each response includes a `nextCursor` field. Pass it as `cursor` in the next request.

## 3. Stale Data Alerts (DAT-24)

> Anexo 07 DAT-24: Automatic notification when data flow stops for > 4 hours.

### Configuration

| Setting | Value | Range |
|---------|------:|------:|
| Default threshold | 4h | — |
| Minimum | 1h | — |
| Maximum | 72h | — |

Configurable per tenant via `settings.staleThresholdHours` in the tenants table.

### Detection Mechanism

```
EventBridge (5 min) → Lambda offlineAlerts
  → Query: meters with no reading in last N hours
  → Create alert (type: METER_OFFLINE, severity: HIGH)
  → Notify: email (SES) + webhook (if configured)
```

### Meter Reading Status

`meter_reading_status` table tracks per-meter last reading timestamp.
Queryable via `GET /api/v1/meters/:id/status` (external API).

### Alert Response

| Field | Value |
|-------|-------|
| `alert_type_code` | `METER_OFFLINE` |
| `severity` | `HIGH` |
| `auto_resolve` | Yes, when data resumes |
| `notification` | Email + webhook |
